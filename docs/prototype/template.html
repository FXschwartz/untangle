The diff you haven’t reviewed yet

A diff viewer with an editor’s navigation. Its left side is your reviewed snapshot: the code as you have already reviewed it. Marking a change reviewed takes it out of the diff. A new push brings back only what changed since you looked. Everything it hides or groups follows four fixed rules, so the same diff always looks the same. No model writes anything.

Must havesyntax highlightinggo to definitionsearchsame input, same view

Changed since v1: there is no analysis written for one PR, and no inferred trust levels. Every number and group below is computed from the git diff and the language server.

How it works

Four fixed rules

Each rule answers one of the pains from the original prompt. None of them needs to understand what the code means. Each only compares text, tokens or the answers of the language server.

Rule 1 · The reviewed snapshot

Pain: a viewed file resets whenever it changes, and you have to hunt for the new part.

Your review lives in a git commit, the base plus every change you marked reviewed. The viewer always shows the diff from that commit to the PR head.

  • Marking a change reviewed applies it to the snapshot, so it drops out of the diff.
  • New commits move the head and leave the snapshot alone. A reviewed region that didn’t change has no diff. A region that changed shows the diff from what you reviewed to what is there now.
  • When the PR is rebased, the snapshot is replayed onto the new base with a 3-way merge, as git merge-file does. Regions that conflict go back to unreviewed.
  • Any diff tool can show what’s left, for example git diff review/168 pr/168. git-tree-compare can compare against any branch in its full mode, so it could show this today.
Rule 2 · Repeated edits

Pain: a changed signature rewrites the same thing at every call site.

Each change is tokenized with the grammar used for highlighting. Whitespace is dropped, and the remaining tokens are diffed. An edit is a run of removed and added tokens between unchanged ones. Two edits are the same when they remove the same tokens and add the same tokens.

  • A bracket only matches a bracket at the same nesting depth.
  • Words in comments and strings never match code.
  • Edits that always occur in the same changes form one group.

In #168 the rule finds 48 groups. Together they cover 226 of the 387 changes, but only 542 of the 4,200 changed lines, because most are one-line call sites. The largest is spaceId → userId, in 157 places across 32 files.

Rule 3 · Changed usages

Pain: a new parameter means a different argument at each call site, so the edits aren’t identical.

For each declaration on a changed line, the viewer asks the language server for its references and keeps the ones inside other changes. They are listed under the declaration and can be marked reviewed together.

In #168, the userId parameter of mergeChanges has 173 changed usages. The new userId of mergeInboundBatch has 9, which rule 2 can’t group because each call passes something different.

Rule 4 · Generated files

Pain: generated files still sit in the file list and the counts.

A file is generated when .gitattributes marks it linguist-generated, or when it matches a generated pattern in the review config. Generated files are listed with their size, and they are never diffed or counted. A reviewedWith rule can tie them to their sources.

# .review.yaml
generated:
  - "**/migrations/**"     # on top of .gitattributes
reviewedWith:
  "**/migrations/**": "**/*.spy.yaml"

In #168 there are 21 generated files with 25,731 lines. Ten come from .gitattributes. The other 11 come from the config, which also catches the test migrations that .gitattributes marks as hand-written.

Two filters, also fixed. Changes that only move whitespace or line breaks are always hidden (#168 has none). A toggle hides changes that only touch comments: 24 against main, and 49 against the 0540639 snapshot.

The must-haves

Highlighting, go to definition and search come from the editor

The first version is a VS Code extension on top of a small core, so the editor provides the three must-haves for every language, the same way it does now in git-tree-compare.

Syntax highlighting

The editor’s grammar colors both sides of the diff. The core uses tree-sitter grammars for its tokens, so matching never depends on the theme.

Go to definition

The right side of the diff is the real file in a checkout of the PR head, so the project’s language server works as usual, including references and hover. The left side is the read-only snapshot.

Search

The editor’s search covers the repository. The extension adds one search that only looks at the changes you haven’t reviewed.

Core: a CLI and a library

It keeps the snapshot branch and computes the groups, usages and generated files. Commands: status, mark, unmark, rebase, groups. Plain git underneath, so any tool can read the result.

VS Code extension

A review tree with files, repeated edits and generated files. VS Code’s multi-file diff editor with the snapshot on the left. Mark actions on hunks. The peek view for repeated edits and changed usages.

Nothing else

No server, no model and no index beyond the language server the editor already runs.

Build order

Each step is usable on its own

  1. Snapshot CLIreview mark <file>[:<hunk>], status and rebase, with the snapshot as a branch. git-tree-compare and git diff can show what’s left from day one.
  2. Groups and generated filesreview groups lists repeated edits, and review mark --group marks one. The .review.yaml rules are applied.
  3. VS Code extensionTree, diff against the snapshot, mark actions, peek, search in unreviewed changes, and changed usages from the language server.
  4. SharingPush snapshots so teammates and agents can see what you reviewed. Optionally sync GitHub’s viewed checkboxes.
For discussion

Open questions

  1. Q1What counts as the same edit? “Same tokens” gives spaceId → userId in 157 places. Requiring the same next token gives 156 and keeps the spaceId ?? line inside mergeChanges apart. The toggle in the viewer switches between the two. Tree-sitter node types would be a third option.
  2. Q2Rebase conflicts. Should a region that conflicts go back to unreviewed, or keep the old review and get a flag?
  3. Q3Where snapshots live. A local branch only, pushed refs/reviews/*, or mirrored to GitHub’s viewed checkboxes?
  4. Q4Declarations and their usages. Should marking a declaration reviewed offer to mark its changed usages in one click, or always go through the list?
  5. Q5Is reviewedWith worth it? The alternative is that generated files never need review.
  6. Q6Removed lines. Is go to definition on the old side needed in v1? It needs a base checkout and a second language-server run.
  7. Q7Diff layout. Unified or side by side by default?
