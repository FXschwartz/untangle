Review by chain, end in the code

A review tool that starts from chains of related changes and ends in the code. A chain follows one change across files: a new parameter, the calls that now pass it, and the function that had to take a parameter in turn. Chains link into a map, so you can see which chains build on which. You read a chain as a graph, focus on one member at a time, and mark the whole chain reviewed at once. Reviewed code stays on screen, muted, and its hunk folds away. Every chain, group and count comes from fixed rules over git, tree-sitter and the language server.

Clicking a graph node focuses on it. A hunk folds when its last change is reviewed, and each view has its own hunks. The palette is dark and the syntax colors are stronger.

How it works

Fixed rules, no judgment calls

Each rule answers a pain from the original prompt. None of them needs to understand what the code means. They compare text, syntax trees and the answers of the language server, so the same diff always gives the same view.

Chains

Pain: one change spans files, and today you rebuild it by jumping between them.

A changed line that uses something declared on another changed line links the two changes. The language server decides what a name refers to. Changes join a chain in five ways:

  • Parameters and local variables pass a chain on. A new parameter, the calls that now pass it, and the parameter those calls needed are one chain.
  • A changed function, method, field or type starts a chain with the changes that use it. A member’s chain and the ripple of its own parameters are one chain.
  • The same change in several places is a chain when it names an identifier, so a rename such as withCurrentNodeHlc → withUserClock is tracked together.
  • A chain takes every change of the members it touches. In test files that means the enclosing test. A doc comment counts with the declaration it documents.
  • Imports and docs follow. A new import joins the chains that use what it imports in that file. A Markdown change that names a chain’s member in backticks joins that chain.

In #168, 339 of the 387 changes fall into 59 chains, 31 of them across files. mergeChanges(userId) is the largest: 184 changes in 38 files, drawn as 11 nodes. recordSyncCheckpoint(spaceId), the userId → spaceId rename, has 16 changes in 6 files.

Why 48 changes stay outside

The rest have nothing a rule can link:

  • 14 only remove code. There is no language server on removed lines, as decided in the v2 review.
  • 13 are Markdown that names nothing in a chain.
  • 12 only change comments of members that are in no chain.
  • 9 are local edits that use only unchanged code or declarations inside the same change.

Removed code is the main gap. One way to close it is to match a removed declaration’s name with removed usages, using tree-sitter on the old side.

Chain of chains

Pain: a big change is several chains that build on each other.

Each chain has a core: the changes of its root’s member. Chain A uses chain B when A’s core uses a function, method, field or type in B’s core. That gives a hierarchy. Chains that nothing uses come first, and each level depends on the next.

In #168 the main family has 47 chains in 9 levels. Tests use mergeChanges(userId), which uses _transactionAs and the recorder wrappers. Those use the space manager and the context locks, which use _UserClock and the cache fields. Ten chains link to no other.

Same change

Pain: the same edit repeated across many call sites.

The tokens of each change are diffed. Each run of changed tokens is an edit, and tree-sitter describes it as one of two things:

  • A token replaced by another, in a role: a reference, a declaration name, a named argument or a type.
  • Complete syntax nodes inserted, removed or replaced.

Edits with the same description are the same change.

In #168: spaceId → userId as a named argument, 156 times. hlcManagerFor → spaceIdFor with .normalizedSpaceId removed, 14 times. 53 groups in all.

Reviewed snapshot

Pain: a viewed file resets whenever it changes.

Your review is a local git branch: the base plus every change you marked reviewed. The viewer diffs it against the PR head, so a new push only brings back what changed since you looked. On a rebase, a syntax-aware merge such as mergiraf replays the snapshot, and regions that still conflict go back to unreviewed.

Display
  • Reviewed code is never hidden. It stays muted, with its diff hidden until you show it.
  • Hunks fold on their own when their last change is reviewed. You can open them again, or fold any hunk yourself. Nothing smaller than a hunk folds.
  • Each view has its own hunks. A chain shows each change with three lines of context, so folding a hunk in one place never folds another.
  • Generated files are never reviewed or counted, and can be opened read-only.
Decided so far

Answers from the v2 and v3 reviews

  1. Same editThe same tree-sitter change, for example one token replaced by another.
  2. RebaseConflicts go back to unreviewed, after a syntax-aware merge such as mergiraf.
  3. StorageSnapshots live locally first.
  4. ChainsA whole chain can be marked reviewed at once. Chains are the main navigation, each with a graph, its total diff and a place in the chain map.
  5. GeneratedNot reviewed, but peekable.
  6. LSPNot on removed lines, for now.
  7. LayoutChoosable, unified by default.
  8. HidingReviewed code is never hidden. Only hunks fold, including on their own when fully reviewed.
  9. GraphClicking a node focuses on it and filters the code to it.
The must-haves

Highlighting, go to definition and search come from the editor

The first version is a VS Code extension on top of a small core. The chain list, the chain map and the graphs live in a side panel. The code opens in the editor’s own diff.

Syntax highlighting

The editor’s grammar colors both sides of the diff. The core uses tree-sitter for its own analysis.

Go to definition

The right side of the diff is the real file in a checkout of the PR head, so the project’s language server works as usual. The same server provides the links that build chains.

Search

The editor’s search covers the repository. The extension adds a search over the changes you haven’t reviewed.

Build order

Each step is usable on its own

  1. Snapshot CLIreview mark, status and rebase with mergiraf, on a local branch. git-tree-compare and git diff can show what’s left from day one.
  2. Analysis coreTree-sitter edits, same-change groups, chains and the chain map from the language server, as in this prototype’s analyze.js.
  3. VS Code extensionChain panel with the map and graphs, the diff against the snapshot, mark actions, peek and search.
  4. LaterSharing snapshots with teammates and agents, and syncing GitHub’s viewed checkboxes.
For discussion

Open questions

  1. Q1Removed code: should a removed declaration’s name link the removed usages, using tree-sitter on the old side? That is most of what is left outside chains.
  2. Q2Should the chain list lead with families? The map could be the first screen, with chains inside it, instead of a list.
  3. Q3Member cohesion: it makes chains complete but larger (persistedUserClock now spans 15 test nodes). Keep it, or show those changes as linked but outside?
  4. Q4Chain order inside a family: by level, as now, or by what is left to review?
  5. Q5Large graphs: collapse busy levels into “+N more”, as now, or group nodes by file?
